## The flow

This is the core flow; understand it before touching anything under `lib/services/ai/` or `lib/widgets/ai/`.

1. **Trigger** — `_organize()` in [home_screen.dart](../../lib/widgets/home/home_screen.dart). An empty multi-selection means "the whole folder"; a non-empty one restricts the scan.
2. **Hint** — `showTitleHintDialog` collects an optional canonical title and a movie/series/auto hint.
3. **Task** — `TaskService.startAnalyze(...)` mints an `AiCancelToken`, inserts a running task, and fires `AiService.analyzeFolder` unawaited. The Tasks tab badge tracks `runningCount`.
4. **Analyze** — `AiService.analyzeFolder` walks the tree (**capped at 400 files**, dotfiles skipped) and hands it to [organize_agent.dart](../../lib/services/organize/organize_agent.dart). Code does everything that has a right answer: `FilenameParser` reads season / episode / year / language tokens, `Grouping` puts one title's videos and their companions (subtitles, artwork, NFOs) in one group, and `JellyfinNaming.plan` spells every path. The model decides only what a group *is* — title, movie or series, year, season, episode offset — through tools (`list_groups`, `list_group_files`, `read_existing_nfo`, `submit_group`, `split_group`, `mark_unsure`), so a 26-episode series is one decision rather than 26 paths to spell identically. Each submission's reply lists the paths it produced and any file it could not place, which is how a wrong season gets corrected before the preview. A large folder is decided in **batches** of at most 12 groups (fewer when the context window is small), each a fresh session seeded with a table of the titles decided so far (`find_decided` looks up the rest), so a session's context does not grow with the folder. A batch that throws is retried once, then its groups are marked failed and the rest go on; an `erratic` or `truncated` batch is not retried, and neither is one whose generation timed out (an `AiTimeoutException`, step 5). The Tasks card shows the fraction of groups decided, and the finished task reports counts (decided, remembered, to review, failed).
5. **Provider** — `OpenAiProvider` (`/chat/completions`) or `GoogleGenAiProvider` (`:streamGenerateContent?alt=sse`), both through `AiHttp.withRetry` on the cancel token's client. `OpenAiProvider` **streams** and times out on *silence*, not duration — 10 min for the first event (model load + prompt processing), 2 min between events. No adapter resends after a timeout, whether its own or a gateway's 408, 504 or 524 — Cloudflare's, when the origin sent no headers within 100 s (`AiHttp.withRetry` never retries those statuses, and every adapter passes `retryTimeouts: false`): either can leave the upstream generating, and billing, the first attempt. Each is thrown as an `AiTimeoutException` — a subtype of `AiNetworkException`, so everything that treats it as settling nothing about the model still does — which is how step 4 knows not to rerun the batch either. Not resending is half of it: the adapter's own wait for the response headers is `AiHttp.post`, which sends an `AbortableRequest` and aborts it when the wait runs out, so the connection is closed rather than left on the client (the cancel token's client lives to the end of the run, and the shared `AiHttp.client` for ever) — a local server that takes one request at a time would otherwise queue the next batch behind the one already given up on. After the headers, closing the stream does the same. A 27B model on LM Studio took 88 s for thirty files, so the old 120 s total failed any real folder, and each retry restarted a generation the server was still running; closing the stream is also what makes a local server stop generating on cancel. A body that is not an event stream is parsed as ordinary JSON, and `stream_options` is dropped if refused. `GoogleGenAiProvider` streams too, on the same silence timeouts (it used to be one `generateContent` with 10 min for the whole reply, which cut off a long generation the server was still billing for); each SSE event is a complete response whose parts are appended, and a relay that ignores `alt=sse` and answers with one object or an array of them is read the same way. It asks Gemini for no reasoning the same way `OpenAiProvider` does — `thinkingConfig.thinkingBudget: 0` → `thinkingLevel: "low"` (Gemini 3's replacement, whose floor is "low") → nothing (2.5 Pro cannot stop thinking) — stepping on a 400 that names the field *and* on a reply that reasoned anyway, since a relay drops an unimplemented `thinkingConfig` silently. Its `completionTokens` is `candidatesTokenCount + thoughtsTokenCount`: Google reports thinking beside the answer, never inside it. A `promptFeedback.blockReason`, or any `finishReason` other than `STOP` / `MAX_TOKENS`, throws and discards whatever text arrived — a blocked answer is a failure, not an empty reply, and returning it made the agent loop read a moderation hit as "the model stopped calling tools". The check is an allow-list because the request-fault reasons (`MISSING_THOUGHT_SIGNATURE`, `UNEXPECTED_TOOL_CALL`, `TOO_MANY_TOOL_CALLS`, `MALFORMED_RESPONSE`, `OTHER`) arrive with HTTP 200 too and keep growing. `MAX_TOKENS` is a real answer, cut short, and `ChatResult.truncated` already says so. The OpenAI-compatible side does the same for `finish_reason`: `content_filter` / Zhipu's `sensitive` throw as filtered, `network_error` throws as `AiNetworkException`, `model_context_window_exceeded` throws with advice about the context budget (a larger output cap would make it worse); an `error` object or MiniMax's non-zero `base_resp.status_code` in a 200 body is reported as the account error it is, and `content` sent as a list of `{type: text}` parts (relays mirroring a backend) is read rather than dropped. The Google key goes in `x-goog-api-key`, never `?key=`. `complete`'s JSON mode (tool-calling `chat` has none) steps down `json_object` → a permissive `json_schema` → none when a 400 names `response_format` (LM Studio accepts only `json_schema`), and the accepted mode is cached per endpoint + model. An OpenAI-compatible profile needs no API key (`AiProviderTypeX.requiresApiKey`); a blank key sends no `Authorization` header at all.

   **`/v1` is appended only to a bare origin.** `http://localhost:1234` is what LM Studio, Ollama and llama.cpp print at startup and what users paste; a URL that already carries a path is left exactly as typed, because a relay routes below its own prefix (`…/api/openai`) and Azure below a deployment name, and appending a version segment there is a 404 whose cause is invisible. The Messages and Gemini adapters, which build a path of their own below the root, first cut back a full endpoint pasted from the vendor's docs (`…/v1/messages`, `…/v1beta/models/<model>:generateContent`, a query string included). A 404 or 405 appends ` — POST <url>` to the error, through `AiHttp.safeUrl` (no query string, no user info — the same form the API log keeps); other statuses do not, because the refused-field learning matches words in the message and a relay's path can contain `function` or `thinking`.

   **A transport failure is never rendered by interpolating the exception.** `package:http` puts the request URL in every `ClientException` it raises, and Google's API used to carry the API key in that URL's query string (it now goes in `x-goog-api-key`), so `'Network error: $e'` printed the key into the settings page and any SnackBar. `AiHttp.describeTransportError` reports the cause alone, and those failures throw `AiNetworkException` — a subclass that marks a failure which settles nothing about the model (the endpoint never answered, or refused for a reason of its own: a bad key, a rate limit, a server error), which is what lets `probeTools` tell a blip from a verdict.

   **The per-server memories** (accepted JSON mode, refused fields, which way of turning reasoning off took, `max_completion_tokens`) are keyed by provider | base URL | model | *SHA-256 prefix of the key*. Two profiles can reach one endpoint through different credentials — a personal and a work account, a gateway that routes by token — and what one was refused says nothing about the other. They used to live in process-wide maps, so every launch paid for the same rejections again (on a cloud platform each step is a billed request); `LearnedStore` now keeps them in `ai_learned.json` for 30 days, and the connection test forgets its route's entry before it runs.

   **The API log** (`ApiLog`, opt-in under Settings → Privacy) writes every request body a provider actually sent — each step of a ladder included — with the status, finish reason, text, tool calls and usage that came back, one JSON line per request in `logs/api-<date>.jsonl`, serially, numbered. Headers are never logged and a URL loses its query string and user info, so no key reaches the file; inline images are replaced by their length, and strings over 2 KB are cut to their first 200 characters and a count. It is the only place the silent choices above can be read afterwards.
6. **Plan** — `OrganizeState.buildPlan` turns the decisions into `OrganizeAction`s. Confidence `< 0.6` → `ActionStatus.needsReview`, and so is every file of a group the model marked unsure or never decided, every file the naming rules could not place, and both of two files planned onto one path: they still appear in the preview rather than silently dropping out of it. A file already at its Jellyfin path gets no action. A run that decides no group at all throws, rather than producing a preview of nothing but flagged rows.
7. **Preview — this is the only dry-run and the only gate.** The AI panel's button says *Preview*, not *Apply*. `OrganizePreviewDialog` lets the user edit `action.target` in place and toggle the undo checkbox, and returns `({bool apply, bool backup})`. Cancel means nothing touched disk.
8. **Apply** — `ApplyController.start()` loops the plan honoring pause/stop, **skipping `needsReview` actions entirely**, calling `applyOrganizeAction` per action.
9. **History** — iff `backup` and at least one move succeeded, a manifest is written for undo.

**Non-obvious invariants:**

- **Only one plan exists app-wide.** A second `analyzeFolder` nulls the current plan immediately — concurrent analyze tasks are last-writer-wins.
- **`AiConfig.contextWindow` is a budget, not a server setting.** Compatible servers fix the context when the model is loaded and accept nothing per request, and local ones do not reject an oversized prompt — they silently drop its front, system prompt first. The app can only send less: every agent tool pages its results, and `AgentRuntime.trimHistory` shrinks the oldest tool results once the history nears the window, estimating through `TokenBudget`, which over-estimates on purpose (three ASCII characters per token, one token per other character). Null means no trimming. The ceiling also comes down by the tool schemas (`AgentRuntime` charges them as `overhead`, since they ride on every request but live outside `messages`) and by the reply's reserve: the window has to hold the prompt *and* the answer.
- **The Settings connection test is a real, tool-shaped turn** (`AiConnectionCheck`), not `GET /models` — listing models passed against LM Studio while every generation request was being rejected. It asks for the greeting *as a `report_greeting` tool call*, with the sampling and reasoning switches a task sends; it used to send a JSON-mode completion, which no task sends, so it spent its first requests learning `response_format` and could pass or fail independently of the tool loop. A plain JSON-mode completion is now only the fallback when the server refuses tools, to tell "refuses tools" from "is down". `AiProvider.detectLimits()` runs alongside it and reads the *loaded* context where a server exposes one (llama.cpp `/props`, LM Studio `/api/v0/models`, Ollama `/api/ps` + `/api/show`, vLLM / OpenRouter `/v1/models`, Google `models/{model}`), preferring it over a model's maximum. The result is shown beside the fields and only applied on the user's click.
- **Sampling comes from per-family presets** ([sampling_presets.dart](../../lib/services/ai/sampling_presets.dart)). The list is ordered and the first match wins, so a more specific family must precede any family whose pattern also matches it (`qwen3.8` before `qwen3`, `deepseek-r1` before every `qwen`). Every row cites the model card; a family with no published values is deliberately absent, because an invented preset looks authoritative. A preset's values are sent **explicitly, neutral ones included** — servers fill gaps with their own defaults (llama.cpp `min_p 0.05`; Ollama forces `temperature` / `top_p` to 1.0 when missing) — and a field a server refuses by name is dropped and remembered per endpoint + model (on Chat Completions and Responses the name is read from OpenAI's `error.param` first, since the prose need not name the field, and from the message's wording when `param` names no field that was sent). A stored `temperature: 0.2` reads as unset (it was the old fixed default, not a choice); saves now use `temperature_override`.
- **Reasoning is off by default** (`AiConfig.thinkingEnabled`). The saved choice is read once, above the adapters: `AiConfig.sampling.thinking` resolves it through the family's preset — a family that always or never reasons is asked for as it runs, a hybrid family and a model no preset knows as saved — and every protocol asks for that value, so what the model page draws is what goes out; no adapter reads the saved choice itself. A family that can only be lowered (gpt-oss) is asked for the least where the protocol has a word for it (`ResolvedSampling.leastEffort`: `reasoning_effort: low` on Chat Completions with no platform field, `reasoning.effort: low` on Responses), whatever was saved: its toggle is locked, so the saved choice is not one the user made, and what the model page draws is what goes out. `platform_profiles_test` holds every protocol's body to that value, one family of each kind. No single field turns it off on every server, and several servers silently ignore the ones they don't know, so `OpenAiProvider` tries `chat_template_kwargs.enable_thinking` → `reasoning_effort: "none"` → Qwen3's `/no_think` in order (Ollama's `/v1` skips the first) and judges each by whether the reply **still reasoned**, never by the absence of an error. The connection test walks those ways; if none takes, settings says so instead of pretending. That ladder is for local servers: on a cloud platform each step is a paid request and the platform documents its own switch, so `ThinkingDialect` ([thinking_dialect.dart](../../lib/services/ai/thinking_dialect.dart)) recognises Zhipu and DeepSeek (`thinking: {type}`) and DashScope (`enable_thinking`) by host and sends that field, both ways, with no ladder — Zhipu lets `chat_template_kwargs` through unread and drops `reasoning_effort: "none"` on GLM-4.x, and DashScope's commercial Qwen never reasons without `enable_thinking: true`. A model that cannot stop reasoning at all — Zhipu's 5.3 generation refuses the switch set to off with a message that does not name it ("该模型始终思考，不支持关闭思考") — is remembered per route (`thinkingOffTried` holds `dialect`), the switch is left off its later requests while thinking is off, and the capability matrix says it always reasons; asking it *on* is still sent, since a refused off says nothing about on. A Messages route whose platform takes thinking as a switch declares `messagesThinkingSwitch` in its `RouteSpec` — MiniMax's `/anthropic`, which takes only `adaptive` and `disabled`, and DeepSeek's, DashScope's and Zhipu's Messages faces, which think unless told not to (measured 2026-09-28; a relay or Anthropic's own host is not one: nothing is sent for off there) — and is sent `thinking: {type: "disabled"}` when off and `{type: "adaptive"}` when on, with no swap to another form; a model there that refuses `disabled` (Zhipu's 5.3 generation with its code 1210; a third-party model on DashScope's face, told off in that face's own `enable_thinking` — "restricted to True"; or a server that knows the field and not that value: `disabled` or `thinking.type` named back) is remembered as on Chat Completions (`dialect` in `thinkingOffTried`) and its later requests with thinking off ask for the least reasoning instead, `output_config: {effort: "low"}` — the second rung of `MessagesOff`, which `PlatformProfiles.messagesOffFor` reads for the adapter's body and for `reasoningRouteFor` alike (measured 2026-09-28 with tools: Zhipu's glm-5.3 then returns no thinking block, 64 output tokens against 1449; glm-5.3-flash, and MiniMax-M2.5 through DashScope, still think a little; `low` is the least value both platforms take — Zhipu's 5.3 answers `medium`, `minimal` and `none` with its "始终思考" — and it cannot go beside `disabled`, which draws the same refusal); the least refused too — in words that name it first, or the field it was translated to, or a model that cannot stop, or that name it anywhere where nothing else was learned — is remembered (`leastEffort` in `thinkingOffTried`) and off sends nothing (an error that names none of those, `thinking` first included, is thrown, as for `disabled`); a server that refused the `thinking` field by name before off is never asked the least — one request per rung, once per model, since what a model does with `disabled` is the model's, not the route's (glm-4.6 takes it beside glm-5.3; MiniMax-M2.7 and DashScope's kimi-k2-thinking take it and think anyway, which only the connection test's "still reasoned" shows; a `thinking` block with neither text nor a signature, kimi-k2.6's when reasoning is not asked for or is turned off (asked on, its block has text), is not reasoning — Claude 5's, empty of text under the default `display`, still carries its signature); a server that does not know the `thinking` field at all — a refusal in the words of an unknown field (Pydantic's "Extra inputs are not permitted", which echoes the refused value beside them, "unknown field"; a sub-field named, `thinking.budget_tokens`, is the value, not the field), or one that refuses thinking and names no value, from either direction — is remembered as the field refused by name (`thinking` and every form in `rejectedFields`), nothing is sent either way, and that says nothing about whether the model reasons; so is a 400 that says no `thinking` but refuses another protocol's field for it — a relay's translation layer passing its upstream's refusal back, `reasoning_effort`, `chat_template_kwargs`, Gemini's `thinkingConfig`, a quoted `reasoning` (`reasoningFieldNames` in [thinking_dialect.dart](../../lib/services/ai/thinking_dialect.dart), the one set of names a request for reasoning goes out under on any protocol) — since what the relay sends for it is not the adapter's to change, and only the field can be read from it, save that "mandatory" or "restricted to True" beside such a name in answer to off is the model that cannot stop; a refusal that names `adaptive` gives up on and still says `disabled`; an error about the thinking blocks in the history teaches nothing here either. Any other Messages route sends nothing when off. How a route switches reasoning after what it has learned is read in one place, `PlatformProfiles.reasoningRouteFor`, which the model page, the capability matrix, the route-switch dialog and Diagnostics all draw from, and which `platform_profiles_test` holds against the bodies the adapters would send: a platform's field sent both ways; the protocol's own (Messages sends `thinking` only when on, Responses sends `reasoning.effort` both ways); on refused while off still goes out (a switch route that refused `adaptive` still says `disabled`); off refused by a model that said it cannot stop, on a Messages switch route (`dialect` in `thinkingOffTried`, the least not yet refused — off asks for the least, `output_config.effort: low`, and on is still sent unless it was refused too, `adaptive` or the field by name; off differs either way, so the toggle stays live, and this outranks both); off refused by a model that said it cannot stop, elsewhere or once the least was refused too (`dialect`, and on a switch route `leastEffort` — off sends nothing and the model reasons at its default, and on is still sent unless on was later refused too — the field by name, or a switch route's `adaptive` — which this outranks); off refused without a reason (Responses' `effortNone`, recorded alike for a model that always reasons and one that cannot reason — off leaves the model's default, on is still sent); sent neither way (the field refused by name, or every Messages form — on a switch route, that is the field itself); or the local ladder. The model page's reasoning toggle is live wherever turning it can change whether the model reasons. A preset family decides for itself: a hybrid family's toggle is live on the saved choice, one that always or never reasons is drawn as it runs and locked, and the mode drawn picks its sampling values. Any other model with a refused switch is drawn as its route runs it and locked: on once the model said it cannot stop reasoning, off once the field is sent neither way (the model's default — a test that still reasons says so, and only the user's own server can change it); a switch route that refused only on, a switch route that asks for the least when off, and a Responses route that refused only `none`, keep the toggle live on the saved choice, since one way still goes out (both, where off asks for the least), and the connection test says what the other does. Where off asks for the least, the line under the toggle says so, and that the model may still reason a little, before any test and after one — it is neither "only with reasoning on" nor advice to turn it off on the server. Any other model that said it cannot stop reasoning, or one a connection test caught reasoning on a Responses route that refused `none`, is said to run only with reasoning on, rather than the user being advised to turn it off on the server. That advice — the server's own model settings, LM Studio named — is given where the server is the user's own, and whose it is comes from two things that never guess (`PlatformProfiles.serverOwner`): the address, which says "the user's own" when it is on this computer or a private network by the names and address blocks reserved for that (`PlatformProfiles.privateHost`: `localhost` and `.localhost`, `.local`, `.internal`, `.home.arpa`; loopback, link-local, RFC 1918, `100.64/10`, `fc00::/7`, the unspecified address, an IPv4 address carried in IPv6) and nothing on a public name; and the declaration, which says "someone else's" for a vendor's platform or a relay's and nothing otherwise — a local platform's profile names software, not whose machine runs it. One voice decides: a private address on a custom or local channel is the user's own; a vendor's or a relay's on a public name is someone else's, and the line says that turning it off has no effect there and the model runs at its default, which holds whatever the route sent for off. None, or two that disagree — a custom or local channel on a public name (a VPS, a cloud with no profile, a relay typed in without its profile, Ollama's hosted API under the Ollama profile), a vendor's or a relay's profile at a private address (a proxy on the network in front of a cloud, or the user's own server under that profile) — is not known, and the line gives both: the server's settings if it is theirs, no effect if it is hosted. The connection test's reading of the server software is not consulted: a public root that answers like vLLM may be anyone's. A Chat Completions or Gemini route with no documented field has nothing to send for *on*, so for a model no preset knows the toggle stays disabled there. The route line above the toggle, for a family that reasons however it is asked (always on, or only to be lowered — its toggle the preset draws on and locked), says that it always reasons, on every route, a working switch included, since off is never sent for it; the capability matrix has nothing to measure for such a family and says the same (`reasoningRefusalText`, the one place both read). Otherwise the line names what will be sent — the platform's field (still, on a switch route that refused only on), the protocol's own, or the ladder — and otherwise says what the capability matrix says of the same route: that off asks for the least (the field named, `output_config.effort: low`), that the model always reasons, runs at its default, or is off by default (Messages, except on a switch route, whose platform may think by default); the matrix leaves the least unmeasured, since it may stop the model or only lower it. The route-switch dialog shows the choice each route's request would carry (`AiConfig.sampling.thinking`, the new route's included before anything is saved on it; for a model no preset knows that is the saved choice, where the model page may draw the route's default instead) and names a platform field where that choice still sends it — `output_config.effort` for off where it asks for the least, and `thinking` for on there wherever the adapter still asks it (`PlatformProfiles.messagesOnFormFor`, the one place the adapter decides the form). Diagnostics reads the same state (`reasoningStepFor`) and fails only what the user can act on. It judges against the choice the test sent (`AiConfig.sampling.thinking`, the one value every adapter asks for), save where the field is sent neither way for a model no preset knows: that saved choice asks nothing (and is usually "on", the refusal mostly being learned while on), so the step, like the model page, treats it as off. A reply that still reasons with off asked for the least is the most the route can do, and the step says that rather than failing; one that shows none there is off. A reply that still reasons with off is the model's default where off was refused (the model said it cannot stop, or Responses refused `none`) and behind a locked toggle with nothing to switch (the ladder for a model no preset knows, a family with no reasoning mode); a family that always reasons is never asked off. Everywhere else it is a failed step, exactly where the model page warns: behind a live toggle — a preset family's included, on the ladder or a refused field — and behind that drawn-off one. Where the model page says the model can only run with reasoning on, a reply that shows none is not taken as off. A request for reasoning the route refused, answered without reasoning, is a failed step where the toggle can turn reasoning off and is only said where it is locked (except on that rare route that cannot stop and later refused on too, where the state does not say); the model page itself shows no verdict with reasoning on, only the refused field.
- **`backup` does not copy anything.** It gates whether an undo manifest is recorded. The name is a misnomer kept for the UI string.
- **`OrganizeAction.target` is deliberately mutable** so the preview dialog can correct the model in memory. This keeps every disk write behind `ApplyController`.
- **The model never writes or names a path.** It points at groups by id and at files by number; `source` is the scan's own relative path and `target` comes from `JellyfinNaming`, so nothing the model says can aim a move outside the folder. Keep new organize tools to that contract.
- **Organizing remembers, keyed by fingerprints** (path + size + mtime, [organize_workspace.dart](../../lib/services/organize/organize_workspace.dart)). A group's decision is saved the moment it is made, so a cancelled or failed run resumes with only the undecided groups; a group changed by `split_group` is never saved, since its files no longer match its fingerprint. Only an *applied* preview's corrections are remembered (`AiService.rememberEdits`) — cancelling means they were never the user's decision — under the file's fingerprint both where it was and where it went, and they win over any decision on the next run. Anything that changes a fingerprint (a re-encode, a cross-volume move that resets mtime) is a miss, never a stale hit, and an unreadable cache is an empty one.
- **Every AI task needs a model that calls tools — there is no single-shot fallback.** The connection test establishes it with its own greeting (a prose reply gets one more ask through `AiConnectionCheck.probeTools`, which asks twice on its own because small models sometimes answer in prose once). The answer is stored on the profile as `ToolSupport`, keyed by provider | endpoint | model, so it goes stale when any of those changes. A never-tested profile is probed on first use by `AiService.ensureTools`, and a model known not to call tools disables Organize and the scrape panel's LLM buttons.

  **The probe has three outcomes, not two.** A server that refuses the `tools` field by name — a 400 or 422 whose message says `tool` or `function`, the same test the connection check's `run` applies — has answered the question (`unsupported`), and so has a model that answers in prose twice (one prose reply beside a failed request was a single chance, and settles nothing). Any other failure has answered nothing (`inconclusive`) and is recorded nowhere: a request that never arrived, a bad key, an empty balance, a rate limit, a server error, a wrong model name. Collapsing them wrote one dropped connection — or one 429 on a model's first run — to the profile as a permanent "this model does not call tools", which stays until a human re-runs the test in Settings, and tells the wrong story to someone whose Wi-Fi went down. `ensureTools` surfaces the real failure instead. The adapters make the split visible in the exception type too: `AiHttp.statusError` turns 401, 402, 403, 408, 429 and every 5xx into an `AiNetworkException` (408, 504 and 524 as its `AiTimeoutException` subtype), anything else into a plain `AiException`, and a non-tools refusal is not asked a second time, nor is a server's or the adapter's timeout (the first greeting may still be generating); the probe's own 90 s cap is asked again, since a local model still loading answers the second ask.
- **Cancellation works by closing the token's own `http.Client`**, so cancellable requests must not use the shared `AiHttp.client`. A socket close surfaces as a generic `ClientException` and is re-mapped to `AiCancelled`.
- `AiService.updateConfig` is called from a widget `build()`, so it early-returns when unchanged and defers `notifyListeners` via a post-frame callback. Breaking either causes "setState() during build".

## Agent runtime

[agent_runtime.dart](../../lib/services/agent/agent_runtime.dart) is the one tool loop that organizing, recipe learning and direct extraction all run through. A task supplies its tools, its own state and a completion check; the protocol obligations live in the loop, once:

- **Every tool call gets a reply.** A cancel mid-round answers the calls it skipped with `notRunResult` before throwing — a history with an unanswered call is rejected on every later turn.
- **A bad call is text, not an exception.** A tool throws `ToolError` phrased as the *next step* ("There is no group "g7". Call list_groups…"), and the model gets another round. Three rounds in a row of nothing but failed calls end the run as `erratic`: a model that cannot drive the tools only burns tokens. A round whose reply hit the output limit (`finish_reason: length`) does not count: its arguments were cut off, which reads exactly like bad JSON. Two such rounds in a row, or a cut-off reply with no tool call, end the run as `truncated`, and the user is told to raise the maximum output rather than to change models.
- **A round that leaves the task done ends the run** (unless `stopWhenDone: false`, which direct extraction uses so the model may keep adding fields), so a small model does not spend a turn announcing it has finished. A model that stops early is nudged at most twice, and **the nudge is retracted once it has been sent** — along with the model's own "I am finished" turn. A reminder left in the history becomes a standing instruction, and organize's carries state ("still undecided: g3, g7") that is wrong by the next round; retracting only the reminder would strand that assistant turn, and then put two assistant turns in a row once the model resumed calling tools, which Gemini rejects.
- **`trimHistory` shrinks old tool results; it never removes a message**, for the same pairing reason.
- Nothing relies on a forced `tool_choice` — some servers accept only `auto` while reasoning.

Underneath, `AiProvider.chat` accumulates OpenAI `tool_calls` fragments by index (a repeated id or name fragment is ignored, since some servers resend them; arguments that arrive as several objects back to back — a relay-served Claude streams an empty `{}` before the real input — are stored merged into one, because a relay translating the turn back to Messages has to parse it; Messages merges a tool input streamed the same way), passes a reasoning field back only on assistant messages that carry tool calls, and keeps Gemini's raw model parts verbatim, because their thought signatures are what the next turn is validated against.

## Channels, routes and models

Read with [ai_channel.dart](../../lib/models/ai_channel.dart), [platform_profiles.dart](../../lib/services/ai/platform_profiles.dart) and [ai_profiles_service.dart](../../lib/services/ai/ai_profiles_service.dart).

- **A channel is one key on one host; a route is one protocol that key speaks there; a model hangs off the channel and picks one route.** Everything below the settings layer still receives one flat `AiConfig` (`AiChannel.configFor`), so providers, the agent loop and the tasks never see channels.
- **Vendor differences are data.** `PlatformProfiles` lists, per platform, the protocols it offers with their default paths, and the reasoning switch per route (`thinking.type`, `enable_thinking`, OpenRouter's `reasoning.enabled`). Every row cites its source. `PlatformProfiles.dialectFor(config)` replaces guessing from the model name (the one choice read from the id is which Claude generation a Messages request asks thinking of, `MessagesThinking.forModel`); a host no profile claims is "custom" and keeps the local-server ladder — exactly the old behaviour.
- **Parameters are per route.** `AiModelEntry.params` keeps one `RouteParams` per protocol; switching routes parks the current values and starts the new route from what it had before, never a copy. The switch dialog shows every row that changes, and "not set · not sent" where nothing was configured — except the thinking row, which shows what the new route's request would carry, since a request asks for reasoning one way or the other before anything is saved.
- **Migration is read-time and byte-identical.** A file without `channels` holds flat profiles; each becomes one channel, one route whose endpoint is the old URL verbatim, one model whose id is the profile id (so the old active profile becomes the organize model, and tool-support fingerprints still match). `ai_profiles_service_test.dart` pins that the migrated config sends the same URL, headers and body as the flat config it came from, for every endpoint shape. One deliberate difference from the build before channels: a profile on a host `PlatformProfiles` now recognises (OpenRouter, Volcengine, beside the Zhipu / DeepSeek / DashScope of P0) gets that platform's reasoning switch instead of the ladder; a model that must reason answers the switch with "mandatory / cannot be disabled", which counts as refusing the field. The file keeps writing a flat `ai_services` mirror and `active_ai_service` — only for models on Chat Completions or Gemini, the two protocols an older build knows — so an older build opened on the same folder still works. Channels on one host, key and platform are offered for merging, and merged only after a confirmation. - **Tasks are assigned.** Organize, scrape-learn, scrape-direct and vision each name a model; an unassigned task follows organize, and deleting a model hands its tasks back to organize. Tool-loop tasks only list models not known to lack tools; vision only models allowed image input.
- **Four protocol families, one adapter each.** `OpenAiProvider` (Chat Completions), `GoogleGenAiProvider` (Gemini), `AnthropicProvider` (Messages) and `OpenAiResponsesProvider` (Responses); a vendor is never a subclass. `AnthropicProvider` repairs the request before sending — alternating roles, a round's tool results grouped into one user turn, system prompt top-level, `max_tokens` always sent, `/v1/messages` added under the route's prefix, `anthropic-version` pinned — and counts input + cache writes + cache reads as the prompt. It asks for thinking as `adaptive` on Claude 4.6 and later and as `enabled` with a budget elsewhere (non-Claude models on a mirror included — no evidence they take `adaptive`; on a switch route, `adaptive` alone, which its platform takes — see above), with `display: "summarized"` on Anthropic's own host only; a refusal that names the form is remembered (`thinking:adaptive` / `thinking:enabled` in the refused fields) and the other form is tried; thinking itself is given up only when the message refuses the feature, and then every form is recorded (a switch route, with one form only, gives up just the form named and still says `disabled` — see above). What a 400 says is read in one place, `MessagesRefusal.read` ([messages_refusal.dart](../../lib/services/ai/messages_refusal.dart)), which returns the one thing to record — a sampling value refused (`OptionalRefused`), a form of thinking or every form given up (`ThinkingFormsRefused`), a rung of off refused (`OffRefused`, naming the rung: `disabled`, then the least reasoning) — or nothing; `chat()` records it through the lesson's own `apply` and sends again, or throws. The text is read once — lower case, the model id taken out (so a relay's `…-thinking` model named in an unrelated error does not count), Pydantic's echoed input (`input_value=…`, the relay's whole translated body when the error is about something else in it) cut out, split into sentences at a full stop or semicolon plus space (not a newline: Pydantic puts a field above its words) — and sentence by sentence. A sentence is about the field it names first: `thinking`, another protocol's name for it (`reasoningFieldNames`), the words of a model that cannot stop, or a sampling value the request sent; the first sentence with a lesson decides. Where off was said as the least reasoning (`output_config: {effort: "low"}`, no `thinking`), a sentence that names `output_config` or `effort` (a word of its own) first — or another protocol's name for thinking, the least being all that could have been translated (Zhipu's "reasoning_effort 参数值非法"), or the words of a model that cannot stop — is that rung refused whatever its words, as a sampling value named first is that value: `low` is all that was sent; `thinking` itself named first is read as ever ("thinking mode does not support top_p" drops `top_p`); and a message that names `output_config` or `effort` where nothing else was learned is the rung refused too, so that no wording fails every request with thinking off (an error that names nothing of it is thrown, as for `disabled`). A rung refused is always the one the request carried, so recording it changes what the route knows and the resend is never the same request. About a sampling value, it is that value's refusal, whatever else it mentions ("`temperature` may only be set to 1 when thinking is enabled", "'top_p' is not supported with reasoning models", "temperature is not supported with thinking" — a switch route told off, with its values beside it, since a request for thinking sends none). About thinking, it is read for what it says of the form asked (the reading `readThinkingRefusal` holds for the vocabulary tests: the model cannot stop, the field unknown, the value refused or merely named, the feature refused, or nothing), one table maps that to the lesson for the direction asked, and where that records nothing a sampling value named in the sentence still is — the first named, again. The rule is the order of the names and nothing finer: "thinking mode does not support top_p" is about thinking and gives it up, the same for `thinking` and a translated name, the price of one rule for all three. So "reasoning_effort is not supported; use temperature instead" gives thinking up and keeps `temperature`, "reasoning is mandatory …; temperature is ignored" is the model that cannot stop, and "Unsupported parameter: reasoning_effort. Supported parameters: temperature, …" leaves the values alone; an error whose link to the thinking docs stands in its own sentence, refusing another field in another, no longer gives thinking up, and one whose refusal and `thinking` fall in different sentences no longer does either — it is thrown. Within a sentence about thinking: unknown-field words are read before the value is looked for; a sub-field named beside a refusal (`thinking.type`, or `thinking.budget_tokens` among extra inputs — the sub-fields a request carries, not "thinking.Please" or a docs URL) is the value, so the form is swapped rather than thinking given up, while a budget named with nothing refused (out of range) is the numbers and teaches nothing; "cannot stop" answers off alone — asked on, those words are read by what stands beside them, the form named or refused; one that says no `thinking` but refuses it under another protocol's name — a relay's translation layer passing its upstream's refusal back, "Unrecognized request argument supplied: reasoning_effort" — is the field unknown (`refusesThinkingTranslated`, in the words of a refusal or of an unknown field — Google's "Unknown name" among them — or with the name quoted): nothing finer can be known, since what the relay sent for it is not ours; the one exception is "mandatory" — or "restricted to True", DashScope's Messages face answering off for a model that only thinks, in its own `enable_thinking` — beside such a name in answer to off: like "always thinks", which names no field, it says the model cannot stop. A name merely mentioned with nothing refused is about something else. A bare `thinking` written before the forms were told apart counts as `enabled` refused where adaptive is asked first (Claude 4.6 and later, a switch route), so an older record does not keep adaptive from being asked; elsewhere `enabled` was the model's own form, and the record still gives thinking up. A budget error, or one about the thinking blocks already in the conversation (a modified block, a signature bound elsewhere), is thrown as it is and teaches nothing. `thinking` and `reasoning` are ordinary words, so they count only quoted, addressed as a parameter, or as a whole word beside a refusal (`reasoning_content` refused in the history is not the field) — `namesField`, the one rule the Chat Completions adapter reads its refused fields by too. Because a relay can also drop the request for thinking without a word, the connection test reports whether the reply reasoned whichever way thinking was asked. `OpenAiResponsesProvider` sends `store: false`, `instructions` every time, tools with `strict: false`, asks for `reasoning.encrypted_content`, takes the finished items of `response.output_item.done` as the truth, accepts a stream without a terminal event only when every item any event began has finished and one of them is text, a refusal or a call (logged as `incomplete_stream`, no finish reason — some relays drop the last event; a stream cut mid-item still fails), and never passes back a reasoning item without its encrypted content (with `store: false` it names an id the server never kept). With thinking off it sends `reasoning: {effort: "none"}` — left out, the model runs at its own default, medium on GPT-5.5 / 5.6 and high on Grok 4.5 / 4.6; a route that refuses it is remembered (`thinkingOffTried` holds `effortNone`, not a refused field, so thinking on still asks for `medium`, or `low` for a family that can only be lowered) and left at the model's default, and a relay that rewrites `none` shows up as reasoning in the connection test. The capability matrix shows it as not measured for that reason, and as the model's default once `none` (or `reasoning` itself) was refused. The Responses, Messages and Gemini adapters read streams through `Sse.read` ([sse.dart](../../lib/services/ai/sse.dart)), which ignores comment / `event:` / `id:` lines and empty `data:`, joins multi-line `data:`, and skips and counts an event that does not parse. Each adapter then decides whether the reply can stand without it: Responses takes the terminal event's own copy of the output when one was skipped, and fails with no copy; Messages and Gemini always fail, since the skipped event could have been a piece of text or of a tool input and the reply would read as whole without it. Messages, like Responses, accepts a stream with no `message_stop` when every block was closed (`content_block_stop`) and one is text or a tool call; Anthropic mirrors also get the key as a bearer token, and a cut-off `tool_use` input goes back as `{}` inside the turn so its thinking block is kept. The Messages and Responses adapters both stream on the same silence timeouts; each has an env-gated live round trip in its test file (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`), skipped in the normal suite.
- **Pass-back is one carrier.** A turn a protocol must receive back unchanged — Gemini parts with thought signatures, Anthropic blocks with thinking signatures, Responses items with encrypted reasoning — rides on the assistant message as a `ProviderTurn` tagged with protocol and model. It goes back verbatim only to that protocol and model; otherwise the turn is rebuilt from its text and calls, because a signature is checked against the model that wrote it. Chat Completions' reasoning passback (`ReasoningPassback`: the reasoning under the field name the server used, sent back only on tool-call turns) also carries Volcengine's `encrypted_content` — its 2.1 models' `reasoning_content` is only a summary — sent back beside the summary, and alone when the summary is empty. It is not a `ProviderTurn` because the history estimate reads a raw turn's parts only, and would lose the text and calls; like the other opaque blobs it is left out of that estimate.

## Frame recognition

For a video whose name says nothing (`VID_20230812.mp4`, a disc rip, an episode with no number), organize can ask what is on screen. [frame_vision.dart](../../lib/services/ai/frame_vision.dart) and [video_frames.dart](../../lib/services/thumbnails/video_frames.dart).

- **Off until the user allows it, for one model.** Frames leave the computer, so consent (Settings → AI access, under the vision task) is off by default and names one model on one endpoint (`SettingsService.visionFramesAllowedFor`): reassigning the task to another model — a cloud one after a local one — reads as off until that one is allowed too. `AiProfilesService.visionConfig` returns a model only when it has image input allowed; the vision task falls back to organize's model only if that model may see images too. Both are read again before every lookup, so withdrawing consent mid-run takes effect at once.
- **The organize model asks; a vision model looks.** `identify_from_frames` is offered only when both hold. It takes a few frames of the group's main (non-extra) video through the thumbnailers the file table uses — at fixed offsets (20 s, 90 s, 5 min, 15 min), 768 px; Windows' Shell thumbnailer takes no timestamp, so there it is one frame — and sends them to the vision model with an instruction to report only on-screen text, never to guess a title from the scenes. The organize model gets that text back as the tool result; the organize model itself never needs to see images.
- **The contract holds.** The vision model reports; the organize model decides what the group is; `JellyfinNaming` builds every path. Once any frames have been read in a run, every later decision is capped at confidence 0.5 with a note — what the frames showed can carry into sibling groups and later batches — and a split keeps the flag on both halves. Five lookups per run at most (each is a paid request with several images).
- **Failures belong to the vision model.** A vision call that fails comes back to the organize model as an ordinary answer ("the frames could not be read"), never as a failed call, so it cannot end the run as `erratic` with advice about the wrong model. Nothing was read, so it flags nothing: a lookup that fails, finds no frames, gets an empty reply or meets withdrawn consent (`FramesUnavailable`) leaves later decisions at their own confidence. A timeout is also the last lookup: one that timed out (`AiTimeoutException` — the adapter's silence timeouts, ten minutes for the headers and again for the first event, two between events, or a gateway's 408 / 504 / 524) uses up the run's remaining lookups, since a vision service silent that long is likely to be so again and a cloud one may still be generating, and billing, the first (in practice the model's reply to "could not be read" is to ask again for the same group); the answer says so, the rest of the run decides from names, and a later batch, a fresh session, is not offered the tool at all (nor once five lookups were spent). A cancel inside any tool rethrows after every call of the round has been answered. Frame extraction checks the cancel token between frames and gives each decode 20 s.
- **Images in messages.** `UserMessage.images` are mapped per protocol (`image_url` data URL, Gemini `inlineData`, Anthropic `image` base64 block, Responses `input_image`), counted at `AgentRuntime.imageTokens` each by the budget, and logged by length only. Native video parts are not sent on any protocol (not measured anywhere); video goes as frames.
