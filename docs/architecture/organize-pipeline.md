# The organize pipeline

> measurements and the history. CLAUDE.md states each rule in a line; this is where
> to look before arguing with one. Keep the two in step.

## The flow

This is the core flow; understand it before touching anything under `lib/services/ai/` or `lib/widgets/ai/`.

1. **Trigger** — `_organize()` in [home_screen.dart](../../lib/widgets/home/home_screen.dart). An empty multi-selection means "the whole folder"; a non-empty one restricts the scan.
2. **Hint** — `showTitleHintDialog` collects an optional canonical title and a movie/series/auto hint.
3. **Task** — `TaskService.startAnalyze(...)` mints an `AiCancelToken`, inserts a running task, and fires `AiService.analyzeFolder` unawaited. The Tasks tab badge tracks `runningCount`.
4. **Analyze** — `AiService.analyzeFolder` walks the tree (**capped at 400 files**, dotfiles skipped) and hands it to [organize_agent.dart](../../lib/services/organize/organize_agent.dart). Code does everything that has a right answer: `FilenameParser` reads season / episode / year / language tokens, `Grouping` puts one title's videos and their companions (subtitles, artwork, NFOs) in one group, and `JellyfinNaming.plan` spells every path. The model decides only what a group *is* — title, movie or series, year, season, episode offset — through tools (`list_groups`, `list_group_files`, `read_existing_nfo`, `submit_group`, `split_group`, `mark_unsure`), so a 26-episode series is one decision rather than 26 paths to spell identically. Each submission's reply lists the paths it produced and any file it could not place, which is how a wrong season gets corrected before the preview. A large folder is decided in **batches** of at most 12 groups (fewer when the context window is small), each a fresh session seeded with a table of the titles decided so far (`find_decided` looks up the rest), so a session's context does not grow with the folder. A batch that throws is retried once, then its groups are marked failed and the rest go on; an `erratic` or `truncated` batch is not retried, and neither is one whose generation timed out (an `AiTimeoutException`, step 5). The Tasks card shows the fraction of groups decided, and the finished task reports counts (decided, remembered, to review, failed).
5. **Provider** — `OpenAiProvider` (`/chat/completions`) or `GoogleGenAiProvider` (`:streamGenerateContent?alt=sse`), both through `AiHttp.withRetry` on the cancel token's client. `OpenAiProvider` **streams** and times out on *silence*, not duration — 10 min for the first event (model load + prompt processing), 2 min between events. No adapter resends after a timeout, whether its own or a gateway's 408, 504 or 524 — Cloudflare's, when the origin sent no headers within 100 s (`AiHttp.withRetry` never retries those statuses, and every adapter passes `retryTimeouts: false`): either can leave the upstream generating, and billing, the first attempt. Each is thrown as an `AiTimeoutException` — a subtype of `AiNetworkException`, so everything that treats it as settling nothing about the model still does — which is how step 4 knows not to rerun the batch either. A 27B model on LM Studio took 88 s for thirty files, so the old 120 s total failed any real folder, and each retry restarted a generation the server was still running; closing the stream is also what makes a local server stop generating on cancel. A body that is not an event stream is parsed as ordinary JSON, and `stream_options` is dropped if refused. `GoogleGenAiProvider` streams too, on the same silence timeouts (it used to be one `generateContent` with 10 min for the whole reply, which cut off a long generation the server was still billing for); each SSE event is a complete response whose parts are appended, and a relay that ignores `alt=sse` and answers with one object or an array of them is read the same way. It asks Gemini for no reasoning the same way `OpenAiProvider` does — `thinkingConfig.thinkingBudget: 0` → `thinkingLevel: "low"` (Gemini 3's replacement, whose floor is "low") → nothing (2.5 Pro cannot stop thinking) — stepping on a 400 that names the field *and* on a reply that reasoned anyway, since a relay drops an unimplemented `thinkingConfig` silently. Its `completionTokens` is `candidatesTokenCount + thoughtsTokenCount`: Google reports thinking beside the answer, never inside it. A `promptFeedback.blockReason`, or any `finishReason` other than `STOP` / `MAX_TOKENS`, throws and discards whatever text arrived — a blocked answer is a failure, not an empty reply, and returning it made the agent loop read a moderation hit as "the model stopped calling tools". The check is an allow-list because the request-fault reasons (`MISSING_THOUGHT_SIGNATURE`, `UNEXPECTED_TOOL_CALL`, `TOO_MANY_TOOL_CALLS`, `MALFORMED_RESPONSE`, `OTHER`) arrive with HTTP 200 too and keep growing. `MAX_TOKENS` is a real answer, cut short, and `ChatResult.truncated` already says so. The OpenAI-compatible side does the same for `finish_reason`: `content_filter` / Zhipu's `sensitive` throw as filtered, `network_error` throws as `AiNetworkException`, `model_context_window_exceeded` throws with advice about the context budget (a larger output cap would make it worse); an `error` object or MiniMax's non-zero `base_resp.status_code` in a 200 body is reported as the account error it is, and `content` sent as a list of `{type: text}` parts (relays mirroring a backend) is read rather than dropped. The Google key goes in `x-goog-api-key`, never `?key=`. `complete`'s JSON mode (tool-calling `chat` has none) steps down `json_object` → a permissive `json_schema` → none when a 400 names `response_format` (LM Studio accepts only `json_schema`), and the accepted mode is cached per endpoint + model. An OpenAI-compatible profile needs no API key (`AiProviderTypeX.requiresApiKey`); a blank key sends no `Authorization` header at all.

   **`/v1` is appended only to a bare origin.** `http://localhost:1234` is what LM Studio, Ollama and llama.cpp print at startup and what users paste; a URL that already carries a path is left exactly as typed, because a relay routes below its own prefix (`…/api/openai`) and Azure below a deployment name, and appending a version segment there is a 404 whose cause is invisible. The Messages and Gemini adapters, which build a path of their own below the root, first cut back a full endpoint pasted from the vendor's docs (`…/v1/messages`, `…/v1beta/models/<model>:generateContent`, a query string included). A 404 or 405 appends ` — POST <url>` to the error, through `AiHttp.safeUrl` (no query string, no user info — the same form the API log keeps); other statuses do not, because the refused-field learning matches words in the message and a relay's path can contain `function` or `thinking`.

   **A transport failure is never rendered by interpolating the exception.** `package:http` puts the request URL in every `ClientException` it raises, and Google's API used to carry the API key in that URL's query string (it now goes in `x-goog-api-key`), so `'Network error: $e'` printed the key into the settings page and any SnackBar. `AiHttp.describeTransportError` reports the cause alone, and those failures throw `AiNetworkException` — a subclass that marks a failure which settles nothing about the model (the endpoint never answered, or refused for a reason of its own: a bad key, a rate limit, a server error), which is what lets `probeTools` tell a blip from a verdict.

   **The per-server memories** (accepted JSON mode, refused fields, which way of turning reasoning off took, `max_completion_tokens`) are keyed by provider | base URL | model | *SHA-256 prefix of the key*. Two profiles can reach one endpoint through different credentials — a personal and a work account, a gateway that routes by token — and what one was refused says nothing about the other. They used to live in process-wide maps, so every launch paid for the same rejections again (on a cloud platform each step is a billed request); `LearnedStore` now keeps them in `ai_learned.json` for 30 days, and the connection test forgets its route's entry before it runs.

   **The API log** (`ApiLog`, opt-in under Settings → Privacy) writes every request body a provider actually sent — each step of a ladder included — with the status, finish reason, text, tool calls and usage that came back, one JSON line per request in `logs/api-<date>.jsonl`, serially, numbered. Headers are never logged and a URL loses its query string and user info, so no key reaches the file; inline images are replaced by their length, and strings over 2 KB are cut to their first 200 characters and a count. It is the only place the silent choices above can be read afterwards.
6. **Plan** — `OrganizeState.buildPlan` turns the decisions into `OrganizeAction`s. Confidence `< 0.6` → `ActionStatus.needsReview`, and so is every file of a group the model marked unsure or never decided, every file the naming rules could not place, and both of two files planned onto one path: they still appear in the preview rather than silently dropping out of it. A file already at its Jellyfin path gets no action. A run that decides no group at all throws, rather than producing a preview of nothing but flagged rows.
7. **Preview — this is the only dry-run and the only gate.** The AI panel's button says *Preview*, not *Apply*. `OrganizePreviewDialog` lets the user edit `action.target` in place and toggle the undo checkbox, and returns `({bool apply, bool backup})`. Cancel means nothing touched disk.
8. **Apply** — `ApplyController.start()` loops the plan honoring pause/stop, **skipping `needsReview` actions entirely**, calling `applyOrganizeAction` per action.
9. **History** — iff `backup` and at least one move succeeded, a manifest is written for undo.

**Non-obvious invariants:**

- **Only one plan exists app-wide.** A second `analyzeFolder` nulls the current plan immediately — concurrent analyze tasks are last-writer-wins.
- **`AiConfig.contextWindow` is a budget, not a server setting.** Compatible servers fix the context when the model is loaded and accept nothing per request, and local ones do not reject an oversized prompt — they silently drop its front, system prompt first. The app can only send less: every agent tool pages its results, and `AgentRuntime.trimHistory` shrinks the oldest tool results once the history nears the window, estimating through `TokenBudget`, which over-estimates on purpose (three ASCII characters per token, one token per other character). Null means no trimming. The ceiling also comes down by the tool schemas (`AgentRuntime` charges them as `overhead`, since they ride on every request but live outside `messages`) and by the reply's reserve: the window has to hold the prompt *and* the answer.
- **The Settings connection test is a real, tool-shaped turn** (`AiConnectionCheck`), not `GET /models` — listing models passed against LM Studio while every generation request was being rejected. It asks for the greeting *as a `report_greeting` tool call*, with the sampling and reasoning switches a task sends; it used to send a JSON-mode completion, which no task sends, so it spent its first requests learning `response_format` and could pass or fail independently of the tool loop. A plain JSON-mode completion is now only the fallback when the server refuses tools, to tell "refuses tools" from "is down". `AiProvider.detectLimits()` runs alongside it and reads the *loaded* context where a server exposes one (llama.cpp `/props`, LM Studio `/api/v0/models`, Ollama `/api/ps` + `/api/show`, vLLM / OpenRouter `/v1/models`, Google `models/{model}`), preferring it over a model's maximum. The result is shown beside the fields and only applied on the user's click.
- **Sampling comes from per-family presets** ([sampling_presets.dart](../../lib/services/ai/sampling_presets.dart)). The list is ordered and the first match wins, so a more specific family must precede any family whose pattern also matches it (`qwen3.8` before `qwen3`, `deepseek-r1` before every `qwen`). Every row cites the model card; a family with no published values is deliberately absent, because an invented preset looks authoritative. A preset's values are sent **explicitly, neutral ones included** — servers fill gaps with their own defaults (llama.cpp `min_p 0.05`; Ollama forces `temperature` / `top_p` to 1.0 when missing) — and a field a server refuses by name is dropped and remembered per endpoint + model (on Chat Completions and Responses the name is read from OpenAI's `error.param` first, since the prose need not name the field, and from the message's wording when `param` names no field that was sent). A stored `temperature: 0.2` reads as unset (it was the old fixed default, not a choice); saves now use `temperature_override`.
- **Reasoning is off by default** (`AiConfig.thinkingEnabled`). No single field turns it off on every server, and several servers silently ignore the ones they don't know, so `OpenAiProvider` tries `chat_template_kwargs.enable_thinking` → `reasoning_effort: "none"` → Qwen3's `/no_think` in order (Ollama's `/v1` skips the first) and judges each by whether the reply **still reasoned**, never by the absence of an error. The connection test walks those ways; if none takes, settings says so instead of pretending. That ladder is for local servers: on a cloud platform each step is a paid request and the platform documents its own switch, so `ThinkingDialect` ([thinking_dialect.dart](../../lib/services/ai/thinking_dialect.dart)) recognises Zhipu and DeepSeek (`thinking: {type}`) and DashScope (`enable_thinking`) by host and sends that field, both ways, with no ladder — Zhipu lets `chat_template_kwargs` through unread and drops `reasoning_effort: "none"` on GLM-4.x, and DashScope's commercial Qwen never reasons without `enable_thinking: true`. A model that cannot stop reasoning at all — Zhipu's 5.3 generation refuses the switch set to off with a message that does not name it ("该模型始终思考，不支持关闭思考") — is remembered per route (`thinkingOffTried` holds `dialect`), the switch is left off its later requests while thinking is off, and the capability matrix says it always reasons; asking it *on* is still sent, since a refused off says nothing about on. A Messages route whose platform takes thinking as a switch declares `messagesThinkingSwitch` in its `RouteSpec` (MiniMax's `/anthropic`, which takes only `adaptive` and `disabled`) and is sent `thinking: {type: "disabled"}` when off and `{type: "adaptive"}` when on, with no swap to another form; a model there that refuses `disabled` — or a server that refuses the `thinking` field outright — is remembered as on Chat Completions (`dialect` in `thinkingOffTried`) and the switch is left off its later requests while thinking is off; an error about the thinking blocks in the history teaches nothing here either. Any other Messages route sends nothing when off. How a route switches reasoning after what it has learned is read in one place, `PlatformProfiles.reasoningRouteFor`, which the model page, the capability matrix and the route-switch dialog all draw from, and which `platform_profiles_test` holds against the bodies the adapters would send: a platform's field sent both ways, the protocol's own (Messages sends `thinking` only when on, Responses sends `reasoning.effort` both ways), on refused (every Messages form, or `adaptive` on a switch route — off still works), off refused (`dialect` or `effortNone` in `thinkingOffTried` — on is still sent, off sends nothing and the model reasons at its default), refused by name and sent neither way, or the local ladder. The model page's reasoning toggle is live only where the switch works both ways. A preset family decides for itself, and its toggle follows the saved choice, which picks its sampling values; any other model is drawn as its route runs it — on once off was refused, off once on or the whole field was — and a route whose off was refused says the model only runs with reasoning on rather than advising the user to turn it off. A Chat Completions or Gemini route with no documented field has nothing to send for *on*, so for a model no preset knows the toggle stays disabled there. The route line above the toggle names what will be sent — the platform's field, the protocol's own, or the ladder — and, once something was refused, says what the capability matrix says of the same route: that the model always reasons, runs at its default, or is off by default.
- **`backup` does not copy anything.** It gates whether an undo manifest is recorded. The name is a misnomer kept for the UI string.
- **`OrganizeAction.target` is deliberately mutable** so the preview dialog can correct the model in memory. This keeps every disk write behind `ApplyController`.
- **The model never writes or names a path.** It points at groups by id and at files by number; `source` is the scan's own relative path and `target` comes from `JellyfinNaming`, so nothing the model says can aim a move outside the folder. Keep new organize tools to that contract.
- **Organizing remembers, keyed by fingerprints** (path + size + mtime, [organize_workspace.dart](../../lib/services/organize/organize_workspace.dart)). A group's decision is saved the moment it is made, so a cancelled or failed run resumes with only the undecided groups; a group changed by `split_group` is never saved, since its files no longer match its fingerprint. Only an *applied* preview's corrections are remembered (`AiService.rememberEdits`) — cancelling means they were never the user's decision — under the file's fingerprint both where it was and where it went, and they win over any decision on the next run. Anything that changes a fingerprint (a re-encode, a cross-volume move that resets mtime) is a miss, never a stale hit, and an unreadable cache is an empty one.
- **Every AI task needs a model that calls tools — there is no single-shot fallback.** The connection test establishes it with its own greeting (a prose reply gets one more ask through `AiConnectionCheck.probeTools`, which asks twice on its own because small models sometimes answer in prose once). The answer is stored on the profile as `ToolSupport`, keyed by provider | endpoint | model, so it goes stale when any of those changes. A never-tested profile is probed on first use by `AiService.ensureTools`, and a model known not to call tools disables Organize and the scrape panel's LLM buttons.

  **The probe has three outcomes, not two.** A server that refuses the `tools` field by name — a 400 or 422 whose message says `tool` or `function`, the same test the connection check's `run` applies — has answered the question (`unsupported`), and so has a model that answers in prose twice (one prose reply beside a failed request was a single chance, and settles nothing). Any other failure has answered nothing (`inconclusive`) and is recorded nowhere: a request that never arrived, a bad key, an empty balance, a rate limit, a server error, a wrong model name. Collapsing them wrote one dropped connection — or one 429 on a model's first run — to the profile as a permanent "this model does not call tools", which stays until a human re-runs the test in Settings, and tells the wrong story to someone whose Wi-Fi went down. `ensureTools` surfaces the real failure instead. The adapters make the split visible in the exception type too: `AiHttp.statusError` turns 401, 402, 403, 408, 429 and every 5xx into an `AiNetworkException` (408, 504 and 524 as its `AiTimeoutException` subtype), anything else into a plain `AiException`, and a non-tools refusal is not asked a second time, nor is a server's or the adapter's timeout (the first greeting may still be generating); the probe's own 90 s cap is asked again, since a local model still loading answers the second ask.
- **Cancellation works by closing the token's own `http.Client`**, so cancellable requests must not use the shared `AiHttp.client`. A socket close surfaces as a generic `ClientException` and is re-mapped to `AiCancelled`.
- `AiService.updateConfig` is called from a widget `build()`, so it early-returns when unchanged and defers `notifyListeners` via a post-frame callback. Breaking either causes "setState() during build".

## Agent runtime

[agent_runtime.dart](../../lib/services/agent/agent_runtime.dart) is the one tool loop that organizing, recipe learning and direct extraction all run through. A task supplies its tools, its own state and a completion check; the protocol obligations live in the loop, once:

- **Every tool call gets a reply.** A cancel mid-round answers the calls it skipped with `notRunResult` before throwing — a history with an unanswered call is rejected on every later turn.
- **A bad call is text, not an exception.** A tool throws `ToolError` phrased as the *next step* ("There is no group "g7". Call list_groups…"), and the model gets another round. Three rounds in a row of nothing but failed calls end the run as `erratic`: a model that cannot drive the tools only burns tokens. A round whose reply hit the output limit (`finish_reason: length`) does not count: its arguments were cut off, which reads exactly like bad JSON. Two such rounds in a row, or a cut-off reply with no tool call, end the run as `truncated`, and the user is told to raise the maximum output rather than to change models.
- **A round that leaves the task done ends the run** (unless `stopWhenDone: false`, which direct extraction uses so the model may keep adding fields), so a small model does not spend a turn announcing it has finished. A model that stops early is nudged at most twice, and **the nudge is retracted once it has been sent** — along with the model's own "I am finished" turn. A reminder left in the history becomes a standing instruction, and organize's carries state ("still undecided: g3, g7") that is wrong by the next round; retracting only the reminder would strand that assistant turn, and then put two assistant turns in a row once the model resumed calling tools, which Gemini rejects.
- **`trimHistory` shrinks old tool results; it never removes a message**, for the same pairing reason.
- Nothing relies on a forced `tool_choice` — some servers accept only `auto` while reasoning.

Underneath, `AiProvider.chat` accumulates OpenAI `tool_calls` fragments by index (a repeated id or name fragment is ignored, since some servers resend them; arguments that arrive as several objects back to back — a relay-served Claude streams an empty `{}` before the real input — are stored merged into one, because a relay translating the turn back to Messages has to parse it; Messages merges a tool input streamed the same way), passes a reasoning field back only on assistant messages that carry tool calls, and keeps Gemini's raw model parts verbatim, because their thought signatures are what the next turn is validated against.

## Channels, routes and models

Read with [ai_channel.dart](../../lib/models/ai_channel.dart), [platform_profiles.dart](../../lib/services/ai/platform_profiles.dart) and [ai_profiles_service.dart](../../lib/services/ai/ai_profiles_service.dart).

- **A channel is one key on one host; a route is one protocol that key speaks there; a model hangs off the channel and picks one route.** Everything below the settings layer still receives one flat `AiConfig` (`AiChannel.configFor`), so providers, the agent loop and the tasks never see channels.
- **Vendor differences are data.** `PlatformProfiles` lists, per platform, the protocols it offers with their default paths, and the reasoning switch per route (`thinking.type`, `enable_thinking`, OpenRouter's `reasoning.enabled`). Every row cites its source. `PlatformProfiles.dialectFor(config)` replaces guessing from the model name (the one choice read from the id is which Claude generation a Messages request asks thinking of, `MessagesThinking.forModel`); a host no profile claims is "custom" and keeps the local-server ladder — exactly the old behaviour.
- **Parameters are per route.** `AiModelEntry.params` keeps one `RouteParams` per protocol; switching routes parks the current values and starts the new route from what it had before, never a copy. The switch dialog shows every row that changes, and "not set · not sent" where nothing was configured.
- **Migration is read-time and byte-identical.** A file without `channels` holds flat profiles; each becomes one channel, one route whose endpoint is the old URL verbatim, one model whose id is the profile id (so the old active profile becomes the organize model, and tool-support fingerprints still match). `ai_profiles_service_test.dart` pins that the migrated config sends the same URL, headers and body as the flat config it came from, for every endpoint shape. One deliberate difference from the build before channels: a profile on a host `PlatformProfiles` now recognises (OpenRouter, Volcengine, beside the Zhipu / DeepSeek / DashScope of P0) gets that platform's reasoning switch instead of the ladder; a model that must reason answers the switch with "mandatory / cannot be disabled", which counts as refusing the field. The file keeps writing a flat `ai_services` mirror and `active_ai_service` — only for models on Chat Completions or Gemini, the two protocols an older build knows — so an older build opened on the same folder still works. Channels on one host, key and platform are offered for merging, and merged only after a confirmation. - **Tasks are assigned.** Organize, scrape-learn, scrape-direct and vision each name a model; an unassigned task follows organize, and deleting a model hands its tasks back to organize. Tool-loop tasks only list models not known to lack tools; vision only models allowed image input.
- **Four protocol families, one adapter each.** `OpenAiProvider` (Chat Completions), `GoogleGenAiProvider` (Gemini), `AnthropicProvider` (Messages) and `OpenAiResponsesProvider` (Responses); a vendor is never a subclass. `AnthropicProvider` repairs the request before sending — alternating roles, a round's tool results grouped into one user turn, system prompt top-level, `max_tokens` always sent, `/v1/messages` added under the route's prefix, `anthropic-version` pinned — and counts input + cache writes + cache reads as the prompt. It asks for thinking as `adaptive` on Claude 4.6 and later and as `enabled` with a budget elsewhere (non-Claude models on a mirror included — no evidence they take `adaptive`), with `display: "summarized"` on Anthropic's own host only; a refusal that names the form is remembered (`thinking:adaptive` / `thinking:enabled` in the refused fields) and the other form is tried; thinking itself is given up only when the message refuses the feature, and then every form is recorded. A bare `thinking` written before the forms were told apart counts as `enabled` refused where adaptive is asked first (Claude 4.6 and later, a switch route), so an older record does not keep adaptive from being asked; elsewhere `enabled` was the model's own form, and the record still gives thinking up. A budget error, or one about the thinking blocks already in the conversation (a modified block, a signature bound elsewhere), is thrown as it is and teaches nothing; the model id is taken out of a message before it is read, so a relay's `…-thinking` model named in an unrelated error does not count. Because a relay can also drop the request for thinking without a word, the connection test reports whether the reply reasoned whichever way thinking was asked. `OpenAiResponsesProvider` sends `store: false`, `instructions` every time, tools with `strict: false`, asks for `reasoning.encrypted_content`, takes the finished items of `response.output_item.done` as the truth, accepts a stream without a terminal event only when every item any event began has finished and one of them is text, a refusal or a call (logged as `incomplete_stream`, no finish reason — some relays drop the last event; a stream cut mid-item still fails), and never passes back a reasoning item without its encrypted content (with `store: false` it names an id the server never kept). With thinking off it sends `reasoning: {effort: "none"}` — left out, the model runs at its own default, medium on GPT-5.5 / 5.6 and high on Grok 4.5 / 4.6; a route that refuses it is remembered (`thinkingOffTried` holds `effortNone`, not a refused field, so thinking on still asks for `medium`) and left at the model's default, and a relay that rewrites `none` shows up as reasoning in the connection test. The capability matrix shows it as not measured for that reason, and as the model's default once `none` (or `reasoning` itself) was refused. The Responses, Messages and Gemini adapters read streams through `Sse.read` ([sse.dart](../../lib/services/ai/sse.dart)), which ignores comment / `event:` / `id:` lines and empty `data:`, joins multi-line `data:`, and skips and counts an event that does not parse. Each adapter then decides whether the reply can stand without it: Responses takes the terminal event's own copy of the output when one was skipped, and fails with no copy; Messages and Gemini always fail, since the skipped event could have been a piece of text or of a tool input and the reply would read as whole without it. Messages, like Responses, accepts a stream with no `message_stop` when every block was closed (`content_block_stop`) and one is text or a tool call; Anthropic mirrors also get the key as a bearer token, and a cut-off `tool_use` input goes back as `{}` inside the turn so its thinking block is kept. The Messages and Responses adapters both stream on the same silence timeouts; each has an env-gated live round trip in its test file (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`), skipped in the normal suite.
- **Pass-back is one carrier.** A turn a protocol must receive back unchanged — Gemini parts with thought signatures, Anthropic blocks with thinking signatures, Responses items with encrypted reasoning — rides on the assistant message as a `ProviderTurn` tagged with protocol and model. It goes back verbatim only to that protocol and model; otherwise the turn is rebuilt from its text and calls, because a signature is checked against the model that wrote it. Chat Completions' reasoning passback (`ReasoningPassback`: the reasoning under the field name the server used, sent back only on tool-call turns) also carries Volcengine's `encrypted_content` — its 2.1 models' `reasoning_content` is only a summary — sent back beside the summary, and alone when the summary is empty. It is not a `ProviderTurn` because the history estimate reads a raw turn's parts only, and would lose the text and calls; like the other opaque blobs it is left out of that estimate.

## Frame recognition

For a video whose name says nothing (`VID_20230812.mp4`, a disc rip, an episode with no number), organize can ask what is on screen. [frame_vision.dart](../../lib/services/ai/frame_vision.dart) and [video_frames.dart](../../lib/services/thumbnails/video_frames.dart).

- **Off until the user allows it, for one model.** Frames leave the computer, so consent (Settings → AI access, under the vision task) is off by default and names one model on one endpoint (`SettingsService.visionFramesAllowedFor`): reassigning the task to another model — a cloud one after a local one — reads as off until that one is allowed too. `AiProfilesService.visionConfig` returns a model only when it has image input allowed; the vision task falls back to organize's model only if that model may see images too. Both are read again before every lookup, so withdrawing consent mid-run takes effect at once.
- **The organize model asks; a vision model looks.** `identify_from_frames` is offered only when both hold. It takes a few frames of the group's main (non-extra) video through the thumbnailers the file table uses — at fixed offsets (20 s, 90 s, 5 min, 15 min), 768 px; Windows' Shell thumbnailer takes no timestamp, so there it is one frame — and sends them to the vision model with an instruction to report only on-screen text, never to guess a title from the scenes. The organize model gets that text back as the tool result; the organize model itself never needs to see images.
- **The contract holds.** The vision model reports; the organize model decides what the group is; `JellyfinNaming` builds every path. Once any frames have been read in a run, every later decision is capped at confidence 0.5 with a note — what the frames showed can carry into sibling groups and later batches — and a split keeps the flag on both halves. Five lookups per run at most (each is a paid request with several images).
- **Failures belong to the vision model.** A vision call that fails comes back to the organize model as an ordinary answer ("the frames could not be read"), never as a failed call, so it cannot end the run as `erratic` with advice about the wrong model. Nothing was read, so it flags nothing: a lookup that fails, finds no frames, gets an empty reply or meets withdrawn consent (`FramesUnavailable`) leaves later decisions at their own confidence. A cancel inside any tool rethrows after every call of the round has been answered. Frame extraction checks the cancel token between frames and gives each decode 20 s.
- **Images in messages.** `UserMessage.images` are mapped per protocol (`image_url` data URL, Gemini `inlineData`, Anthropic `image` base64 block, Responses `input_image`), counted at `AgentRuntime.imageTokens` each by the budget, and logged by length only. Native video parts are not sent on any protocol (not measured anywhere); video goes as frames.
